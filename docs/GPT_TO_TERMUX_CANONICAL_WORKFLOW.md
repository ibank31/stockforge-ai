# GPT-to-Termux StockForge: Canonical End-to-End Workflow

**Status:** Canonical operating instruction for GPT and all StockForge agents  
**Audience:** GPT, human operator, and future StockForge agents  
**Execution rule:** GPT reasons and gives commands. Termux executes commands. Never pretend that a command was executed unless Termux output is present.

## 1. Roles and boundaries

GPT is the project brain. GPT reads the repository context, chooses a candidate, decides JPEG versus PNG from the buyer job, writes the prompt, interprets Termux output, and decides the next safe step.

Termux is the executor. Termux runs the local repository, Python CLI, GitHub CLI, Hugging Face commands, Kaggle commands, file copies, audits, and status checks. Termux is not the creative decision-maker.

GitHub stores the code, tests, documentation, worker definitions, and history. Hugging Face may provide an external renderer or remote provider. Kaggle provides the protected GPU finalizer. Android storage holds only source/preview/ready visual files in the designated visual folders.

GPT must never claim success without terminal evidence. GPT must never print, request, commit, or expose Kaggle/Hugging Face credentials.

## 2. The only two approved production flows

### Flow A — Internal StockForge renderer

Use this when the initial image is generated by StockForge's configured internal renderer.

```text
GPT reads repo and selects one candidate
  → GPT creates or selects a repository-backed plan and brief
  → Termux runs dry-run and pre-GPU validation
  → Termux runs exactly one internal preview generation
  → StockForge records artifact, execution, provenance, audit, and learning
  → preview goes to PREVIEW_TO_MANUS
  → human reviews preview and replies KEEP/REJECT/REVIEW
  → after KEEP, Termux prepares the matching JPEG or PNG finalizer request
  → human confirms GPU submission
  → Termux submits exactly one matching Kaggle job
  → Termux waits for COMPLETE and downloads output to project workspace
  → Termux matches request_id and checksum
  → StockForge imports and audits the master
  → human performs full-resolution visual review
  → metadata/package is prepared
  → only the visual master is exported to READY_UPLOAD_ADOBE
  → user uploads manually
```

### Flow B — External renderer, StockForge processing

Use this when GPT Image, ChatGPT, or another approved external renderer creates the initial image.

```text
GPT reads repo and selects one candidate
  → GPT writes one detailed external-renderer prompt
  → user renders exactly one image outside StockForge
  → user copies one source into ~/.stockforge/incoming/external/
  → Termux runs portfolio import-external
  → StockForge records hash, provenance, artifact, execution, audit, and learning
  → preview goes to PREVIEW_TO_MANUS
  → human reviews preview and replies KEEP/REJECT/REVIEW
  → after KEEP, Termux prepares the matching JPEG or PNG finalizer request
  → human confirms GPU submission
  → Termux submits exactly one matching Kaggle job
  → Termux waits for COMPLETE and downloads output to project workspace
  → Termux matches request_id and checksum
  → StockForge imports and audits the master
  → human performs full-resolution visual review
  → metadata/package is prepared
  → only the visual master is exported to READY_UPLOAD_ADOBE
  → user uploads manually
```

The only difference between the flows is who creates the initial image. All post-render handling is controlled by StockForge.

## 3. Universal format decision

| Buyer job | Route | Initial image | Finalizer | Required review |
|---|---|---|---|---|
| Self-contained scene, environment, narrative composition, illustration with background, hero image, copy-space visual | JPEG | RGB/raster scene | Protected Kaggle RealESRGAN | Composition, context, anatomy, artifacts, text/logo/IP risk, full-resolution quality |
| Reusable isolated object, cutout, sticker, overlay, transparent utility asset | PNG | Object intended for transparency | Isolated Kaggle BiRefNet | Alpha at 100%, halos, holes, missing details, edge clipping, unwanted shadow/background |
| Editable geometry or real vector deliverable | SVG/vector | Not active for automatic production | No JPEG/PNG finalizer | Do not route through raster workers |

Choose from the buyer job and background requirement, never from the filename. Never mix JPEG and PNG workers.

## 4. Standard Termux setup

Every Termux operation begins with:

```bash
cd "$HOME/stockforge-ai"
export PYTHONPATH="$PWD/src"
export STOCKFORGE_HOME="${STOCKFORGE_HOME:-$HOME/.stockforge}"
```

The active project workspace is normally:

```text
/storage/emulated/0/StockForge/projects/stock-assets/
```

If a command needs a project-relative path, use the actual path emitted by StockForge. Do not invent an artifact ID, execution ID, plan path, request ID, or output path.

## 5. Flow A command sequence

First inspect lanes and format policy without generating:

```bash
python3 -m stockforge.cli portfolio lanes
python3 -m stockforge.cli portfolio asset-types
```

GPT then chooses one repository-backed plan and brief. Use the exact plan path and `brief_id` emitted by StockForge. Run the dry-run first:

```bash
python3 -m stockforge.cli portfolio generate --dry-run \
  --project stock-assets \
  --plan <plan-file> \
  --brief-id <brief-id>
```

Only after the dry-run passes may Termux run one live internal preview:

```bash
python3 -m stockforge.cli portfolio generate \
  --project stock-assets \
  --plan <plan-file> \
  --brief-id <brief-id>
```

The preview is exported to:

```text
/storage/emulated/0/Download/MACHINE STOCKFORGE/PREVIEW_TO_MANUS/
```

Stop and wait for the human decision. `KEEP` is required before any finalizer preparation or GPU submission. Do not perform blind seed retries and do not revive the retired batch runner.

After KEEP, use the execution ID emitted by the live generation:

```bash
python3 -m stockforge.cli portfolio workflow-keep \
  --project stock-assets \
  --execution <execution-id>

python3 -m stockforge.cli portfolio prepare-external-finalizer \
  --project stock-assets \
  --execution <execution-id>
```

Use the actual command/help output from the installed CLI if a subcommand name differs. Verify the generated request route before submission. JPEG must target the protected RealESRGAN worker. PNG must target the isolated BiRefNet worker.

After an explicit GPU confirmation, submit one request only:

```bash
python3 -m stockforge.cli kaggle-finalizer submit \
  --project stock-assets \
  --request <jpeg-request.json> \
  --accelerator NvidiaTeslaT4
```

or:

```bash
python3 -m stockforge.cli kaggle-png-finalizer submit \
  --project stock-assets \
  --request <png-request.json> \
  --accelerator NvidiaTeslaT4
```

## 6. Flow B command sequence

GPT first provides the external prompt and waits while the user renders one image outside StockForge. The user then copies one source file:

```bash
mkdir -p "$HOME/.stockforge/incoming/external"
cp "/storage/emulated/0/Pictures/<external-file>" \
  "$HOME/.stockforge/incoming/external/<candidate-id>-source.png"
```

Import one source and preserve the original:

```bash
cd "$HOME/stockforge-ai"
export PYTHONPATH="$PWD/src"
export STOCKFORGE_HOME="${STOCKFORGE_HOME:-$HOME/.stockforge}"

python3 -m stockforge.cli portfolio import-external \
  --project stock-assets \
  --source "$HOME/.stockforge/incoming/external/<candidate-id>-source.png" \
  --candidate-id <candidate-id> \
  --provider chatgpt
```

This import records source hash, provider provenance, candidate linkage, artifact, execution, technical audit, and learning record. It does not call ZeroGPU, Kaggle, Adobe, or a finalizer.

The import preview goes to:

```text
/storage/emulated/0/Download/MACHINE STOCKFORGE/PREVIEW_TO_MANUS/
```

Stop and wait for the human decision. After KEEP, prepare the matching finalizer:

```bash
python3 -m stockforge.cli portfolio workflow-keep \
  --project stock-assets \
  --execution <import-external-execution-id>

python3 -m stockforge.cli portfolio prepare-external-finalizer \
  --project stock-assets \
  --execution <import-external-execution-id>
```

JPEG preparation creates an immutable RGB JPEG staging source that keeps the external composition and remains under the Kaggle kernel source budget. PNG preparation fits the complete source into a 1024×1024 RGB artifact without crop; the BiRefNet worker creates the final alpha output. Neither preparation overwrites the original source.

Then submit exactly one matching worker request after explicit GPU confirmation:

```bash
python3 -m stockforge.cli kaggle-finalizer submit \
  --project stock-assets \
  --request <jpeg-request.json> \
  --accelerator NvidiaTeslaT4
```

or:

```bash
python3 -m stockforge.cli kaggle-png-finalizer submit \
  --project stock-assets \
  --request <png-request.json> \
  --accelerator NvidiaTeslaT4
```

## 7. Kaggle status, download, and matching rules

Check status without submitting again:

```bash
python3 -m stockforge.cli kaggle-finalizer status
python3 -m stockforge.cli kaggle-png-finalizer status
```

When the selected kernel is COMPLETE, download into the project workspace, not into an Android visual folder:

```bash
python3 -m stockforge.cli kaggle-finalizer output \
  --project stock-assets \
  --destination <project-workspace>/kaggle-finalizer-output/<run-label> \
  --force
```

or:

```bash
python3 -m stockforge.cli kaggle-png-finalizer output \
  --project stock-assets \
  --destination <project-workspace>/kaggle-png-finalizer-output/<run-label> \
  --force
```

The `result.json` file is usually inside the kernel output subdirectory. Read the actual downloaded path; do not assume it is at the destination root.

A result is importable only when all of these match the submitted request:

```text
request_id
source/input checksum where recorded
format and route
expected dimensions
color mode/profile
finalizer provider
```

A COMPLETE status alone is insufficient. If the request ID differs, treat the output as an older or unrelated result and do not import it.

## 8. Master import, audit, metadata, and delivery

After matching the result, use the format-specific master-import command: `portfolio import-kaggle-master` for JPEG or `portfolio import-kaggle-png-master` for PNG. Both commands verify request/result identity, checksum, target dimensions, and local technical gates before registering immutable preview-to-master lineage. PNG then uses `portfolio prepare-adobe-png-upload`; JPEG uses `portfolio prepare-adobe-upload`. Neither command submits to Adobe.

Run the technical audit and preserve its report. Then perform human full-resolution review. A state such as `visual_review_required` is not an error and is not marketplace approval.

Only after the master passes the technical gate and human review may the visual-only exporter be used:

```bash
python3 -m stockforge.cli portfolio export-ready-visual \
  --project stock-assets \
  --master <audited-master-path> \
  --approved
```

The exact options must follow `python3 -m stockforge.cli portfolio export-ready-visual --help` in the active checkout. The exporter accepts both JPEG and PNG, applies the matching technical gate, and may copy only the approved visual master:

```text
/storage/emulated/0/Download/MACHINE STOCKFORGE/READY_UPLOAD_ADOBE/
```

The Android visual contract is:

```text
PREVIEW_TO_MANUS/
└── preview visual only

READY_UPLOAD_ADOBE/
└── audited final visual only
```

Never copy JSON, logs, reports, request files, result files, WebP files, intermediate images, model weights, checksums, databases, or ZIP bundles into either visual folder.

## 9. Human decision protocol

The human decisions are intentionally minimal:

| Human response | GPT/Termux action |
|---|---|
| `REVIEW` | Keep the workflow stopped and report what must be inspected |
| `REJECT` | Record rejection and stop the route; do not finalize |
| `KEEP` | Prepare the format-specific finalizer; still request explicit GPU confirmation |
| `FINALIZE` | Submit only the selected request after verifying route and request ID |
| `READY` | Export only the audited master visual; do not submit to Adobe automatically |

GPT may recommend a decision, but it must not invent a human KEEP or visual approval.

## 10. Non-negotiable safety rules

Never change or delete the protected JPEG/PNG workers during an asset run. Never route JPEG through the PNG worker or PNG utility assets through the JPEG worker. Never submit before KEEP. Never retry a failed remote job blindly. Never treat a kernel's COMPLETE status as proof that its output belongs to the latest request. Never force-push, reset, rebase, or delete branches without explicit instruction. Never expose or commit credentials. Never claim sales potential, marketplace approval, or Adobe readiness without the corresponding audit and package support.

If a command fails, preserve its output, stop that route, and report the exact error. Do not silently substitute a different request, candidate, source, or kernel output.

## 11. Current readiness statement

The JPEG route is the mature production route: internal or external source, preview, KEEP gate, protected RealESRGAN finalizer, master audit, metadata/package, and visual export are established.

The PNG route is now end-to-end: isolated BiRefNet preparation/finalization, checksum-checked master import, RGBA/true-alpha/sRGB technical gate, immutable registry lineage, embedded PNG metadata, manual upload bundle, and visual-only export to `Download/MACHINE STOCKFORGE/READY_UPLOAD_ADOBE`. The result remains `visual_review_required` until the user completes the 100% visual edge review and passes `--approved`.

The internal Z-Image batch workflow is retired. The external-renderer adapter is supported. The local llama.cpp/Qwen trial is not part of the production workflow.

## 12. GPT operating instruction

When GPT is connected to this repository, it must read this file first, then read the candidate/backlog and relevant format documents. GPT must answer in this order:

```text
1. candidate and buyer job
2. JPEG/PNG decision with reason
3. prompt or next Termux command
4. expected output location
5. stop condition and required human decision
```

GPT must give one command block at a time when an output or ID from the previous command is required. It must not invent placeholders as if they were real values. It must distinguish clearly between “command to run,” “command executed,” and “result verified.”

This file is the canonical GPT-facing workflow. If another document conflicts with it, follow this file and report the conflict.
